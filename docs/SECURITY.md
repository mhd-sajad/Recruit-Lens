# Recruit Lens Security Architecture and OWASP Audit

This document outlines the security controls, threat mitigations, and accepted risks for the Recruit Lens recruiter platform.

---

## 1. Threat Model & Security Controls

| Vulnerability Category | OWASP Ref | Defense Mechanism Implemented | Enforcement Location |
| :--- | :--- | :--- | :--- |
| **Broken Access Control** | A01:2021 | Strict tenant isolation via `UserScopedMixin` (`user_id == current_user.id`). Foreign key constraints with cascade deletes. Role-based access control (`require_role`). | `app/auth/dependencies.py`, all routers |
| **Cryptographic Failures** | A02:2021 | Passwords hashed using Argon2id (`argon2-cffi`). JWT tokens signed with HMAC-SHA256 and rotated with reuse/theft detection. TLS 1.3 enforced in production. | `app/auth/security.py`, `app/api/v1/auth.py` |
| **Injection (SQL & Code)** | A03:2021 | Exclusively parameterized queries via SQLAlchemy 2.0 ORM. Zero string concatenation in database statements. | `app/db/models.py`, `app/db/session.py` |
| **Prompt Injection** | LLM:01 | Multi-layer defense: Regex sanitizer (`detect_and_neutralize_injections`), strict XML boundaries (`<evidence_chunk>`), Self-RAG grounding critic with blocking threshold. | `app/llm/guardrails.py`, `app/llm/critique.py` |
| **Insecure Design (Bias/PII)**| A04:2021 | Blind Evaluation Mode: automatic regex redaction of candidate names, emails, phone numbers, postal addresses, dates of birth, and universities before LLM prompt submission. | `app/llm/guardrails.py` |
| **Security Misconfiguration** | A05:2021 | Strict HTTP response headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Strict-Transport-Security`, `CSP`). Gitleaks secret scanning across full git history. | `app/main.py`, `.pre-commit-config.yaml`, CI |
| **Vulnerable & Outdated Components**| A06:2021 | Continuous vulnerability scanning: `pip-audit` for Python dependencies (0 vulnerabilities), `npm audit` for frontend. | `pip-audit`, GitHub Actions CI |
| **Identification & Auth Failures** | A07:2021 | Token bucket rate limiting, daily LLM token caps (`DAILY_TOKEN_BUDGET`), short-lived access tokens (15m) + refresh tokens (7d). | `app/config.py`, `app/api/v1/auth.py` |
| **Software & Data Integrity** | A08:2021 | Magic byte verification on file upload (`%PDF`), 15MB file size limit, formula-injection sanitization on CSV export (`sanitize_csv_cell`). One-time confirmation token for MCP mutations. | `app/api/v1/resumes.py`, `app/api/v1/evaluations.py`, `app/mcp/server.py` |
| **Security Logging & Monitoring** | A09:2021 | Immutable `AuditLog` table capturing every state change, decision, and export. Zero PII in application log output. Structured JSON logging with trace `request_id`. | `app/logging.py`, `app/db/models.py` |
| **Server-Side Request Forgery** | A10:2021 | Direct file upload used; external network requests strictly bounded to validated HTTPS endpoints (Groq API, Supabase) with private subnet IP blocking. | `app/core/security.py` |

## 3. Human Confirmation Policy for Agents & MCP
Any autonomous agent or MCP client (e.g., Claude Desktop, IDE extension) connecting via `app/mcp/server.py` is restricted to read-only tools (`list_jobs`, `search_candidates`, `get_candidate_report`, `draft_email`).

Stage transitions and recruitment decisions (`make_decision`) strictly mandate a single-use confirmation token (`McpConfirmationToken`) generated by a human recruiter within the Recruit Lens Web UI. This prevents unauthorized automated candidate rejections or advancements.
