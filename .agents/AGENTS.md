# Project-Scoped Rules for Recruit Lens

The following operating principles must be followed strictly:

1. **VERIFY, DON'T JUST ASSERT.** When you say something is "done," "fast," "safe," or "validated," back it with the actual number, test output, or benchmark that proves it — not a description of what should be true. If you haven't measured something, say so explicitly instead of implying it's fine.

2. **TREAT SECURITY AS STOP-THE-LINE, NOT A FOOTNOTE.** If you find a credential, a secret, an exposed key, or anything similar, stop what you're doing, report it immediately and completely (including anywhere it might have propagated — other remotes, forks, caches, deploys), and wait for confirmation before continuing. Don't bury it in a status update alongside unrelated progress.

3. **QUESTION A DESIGN BEFORE YOU BUILD ON TOP OF IT.** Before the next agent/module depends on a previous one's output, sanity-check that previous piece for hidden costs: does it scale linearly, does it have a failure mode under load, is there an edge case nobody's tested. Raise this before it's buried under three more layers of code.

4. **MATCH THE TOOL TO THE PROBLEM'S ACTUAL SHAPE.** Closed-vocabulary, well-patterned problems (years of experience, seniority titles, structural JD fields) should be solved with regex/rules/lookup tables — fast, deterministic, testable. Open-vocabulary, synonym-heavy problems (skills, free-text resume language) need embedding-based or taxonomy-backed matching, not plain string matching. Don't reach for an LLM call where a deterministic rule works, and don't reach for regex where the problem is genuinely open-ended. If you're not sure which kind of problem you're facing, say so and propose both options with the tradeoff, rather than silently picking one.

5. **RAG GROUNDING IS NON-NEGOTIABLE.** Every piece of generated text (explanations, interview questions, email drafts) must trace back to retrieved evidence chunks. If you're about to generate something without a retrieval step feeding it, stop and add the retrieval step first.

6. **WORK IN SMALL, REVIEWABLE INCREMENTS.** Commit and push after every individual working piece, not after a whole feature is finished. Write the test before or alongside the code, not after. This makes each change independently reviewable and independently revertable if something's wrong.

7. **WHEN REPORTING PROGRESS, INCLUDE WHAT COULD BE WRONG, NOT JUST WHAT WORKS.** After finishing something, explicitly list untested edge cases, known limitations, or things you're assuming rather than have verified. A report that only lists successes is incomplete — the failure modes are as important as the passing tests.

8. **DEFAULT SENSIBLY ON NARROW CHOICES, BUT SURFACE GENUINE TRADEOFFS.** For small implementation details with one clearly reasonable answer, just pick it and move on. For real architectural forks (e.g., "should this scale later" or "which library"), lay out 2-3 options with what each costs/gains, rather than picking silently or asking a vague open question.

9. **DON'T LET "IT WORKS" SUBSTITUTE FOR "IT'S REVIEWED."** Finishing a build step is not the same as it being approved to move forward on. Always pause for review at the checkpoints defined in the project instructions, even if everything passed locally.

10. **KEEP PROJECT_EXPLAINED.md LIVING.** Every time a new commit adds something meaningful (a new agent, a new feature, a new integration, a fix to something significant), you MUST add a new entry to Section 4 of docs/PROJECT_EXPLAINED.md using the exact template defined there BEFORE moving on to the next piece of work. If Section 1, 2, or 3 needs updating because something changed, update those too and note briefly what changed and why. This is part of what 'done' means for a commit.

11. **NEVER READ SHELL HISTORY, TRANSCRIPTS, DOTFILES, OR UNAPPROVED EXTERNAL PATHS.** Do not read shell history, transcript files (`transcript.jsonl`, `transcript_full.jsonl`), `~/.gemini`, or user dotfiles (`.zshrc`, `.bashrc`, `.bash_history`, `.zsh_history`, etc.) or anything outside this repository except the explicitly authorized read-only sources (`~/recruit_lens_vault` and `/home/sajad/PROJECTS/RESUME AND JOB DESCRIPTION/data`). Never inspect or copy content from unauthorized external files. Never open, print, read, or log `.env`; read secrets only through settings module. If you lose instructions, say so and ask the user.

12. **REPORT INTEGRITY (MANDATORY ENFORCEMENT).**
- Reports are generated by a script (`scripts/make_report.py`) that reads `docs/*.json` and `data/*.csv` and prints each number with `file:key`. Never type a number by hand. A number with no file is written "not measured".
- Never name resume IDs, example queries or sample text unless a command printed them in this session. Paste raw command output for any examples.
- Retract in writing every figure from your last report that was not read from a saved file.
- Never open or print .env or shell history. Do not use transcripts.

13. **REPORT SCRIPT AND STRICT AUDIT RULES.**
- `scripts/make_report.py` must exit non-zero and print `MISSING <file:key>` for any key it cannot read. It must never default to 0, [], or "not measured". A missing metric is NOT DONE.
- No hand-written content in a report: no checklists, explanations, coverage tables or percentages typed by hand. Test status comes from pytest output saved to a file; coverage from coverage.json; route lists from the app's OpenAPI; a stated cause must cite the measurement that shows it.
- Merge to main only after CI is green on the branch. Tag only after CI is green on main for that exact commit. Report run IDs and conclusions, including failures and reruns. A tag made on an unverified commit is not moved: make a new tag on a verified commit and record it.
- Never edit a test to make it pass without showing the diff and the reason in the report. Never lower a quality bar to pass a test.

14. **AUDIT & SPEC INTEGRITY RULES.**
- A metric must measure the thing it names. A number computed from the reviewer's labels, or graded by your own keyword lists, is not a measurement of the parser. Label self-graded numbers "self-graded" and never put them in a pass/fail table.
- Every figure in a report comes from a saved file with file:key, and make_report.py exits non-zero on any missing key.
- Test counts come from saved pytest output (junit xml), never from coverage.json.
- No feature or test without a requirement in docs/SPEC.md. Do not add webhooks or roles the SPEC does not have.

## Decision Principles
- Priority order: correctness and safety, then explainability, then simplicity, then speed, then polish.
- Prefer boring, proven, light dependencies. Free-tier hosting means small RAM and ephemeral disk.
- Measure before choosing. Record each non-trivial decision, its alternatives and why you rejected them in docs/PROJECT_EXPLAINED.md.
- Never claim an accuracy you did not measure. State limits plainly.
- Decide yourself. Ask me only when you need my account, key or a physical action, and ask at the end of the batch with your recommended default.

## Working Contract
- Do as much of this batch as you can in one run with no compromise on quality. If you must split, split at a natural boundary, keep going without asking permission, and report where you stopped.
- Commit and push after every working piece (feature branch per task group, merge to main when tests pass, conventional commit messages). Tag a release at the end of each batch (v0.1.0 for this batch, then v0.2.0 and so on).
- Tests with every piece. No TODOs or dead code left behind.
- HARD STOPS (only these): a secret appears in any file or history; you need my credentials or a manual action; something would modify anything outside this repo; force-moving or deleting a pushed tag, or rewriting pushed history (if a tag is wrong, create a new one like v0.3.1; tag only after CI is green on that commit). Anything else: decide, record, continue.

- End every batch with the report format:
  1. Built (bullets).
  2. Tests: counts and pass rate.
  3. Metrics table (real numbers, with what could be wrong).
  4. Decisions made and why.
  5. Known limitations.
  6. What I must do before the next batch.

## Global Quality Bars (Apply to Every Batch)
- Backend: typed code, ruff clean, tests on core logic at 80% coverage or better, 4xx (never 5xx) on bad input, structured logs with request IDs, no PII in logs.
- Backend process stays under 400 MB RSS with one batch loaded. Retrieval plus scoring under 0.5 s per candidate. A 200-resume batch finishes in under 5 minutes excluding LLM text generation.
- Every generated sentence carries citations to evidence chunks. Unsupported text is rewritten or blocked.
- Frontend: strict TypeScript, keyboard-accessible, labelled inputs, loading/empty/error state on every screen.
- Zero secrets in the repo or history (gitleaks in pre-commit and CI).
